## 4. 배운 점

### 4.1 요구사항 정의

- 요구사항 정의서에는 구현 디테일이 아닌 사용자가 경험하는 기능/플로우 자체가 바뀐 것만 반영하면 된다

### 4.2 ERD 설계

- **내부 PK와 외부 노출용 UUID 분리**
    - 외출에 노출될 수 있는 엔티티는 내부 PK와 별개로 UUID를 두는게 좋다.
    - 예를 들어, USER 엔티티는 URL에 노출될 수 있는데, 순차 증가하게 해둔 PK를 URL에 노출하면 다른 사용자의 프로필에 접근을 시도할 수 있게 된다. 이를 방지하기 위해 외부 노출용 UUID를 따로 두는 것이 좋다.
- **ERD 설계 자료형**
    - string vs. varchar : ERD 설계에서는 특정 DB의 자료형이 추상(논리적) 타입인 string을 사용한다.
    - string vs. text : 둘 다 추상 타입이지만 string은 짧고 길이가 예측 가능한 문자열(이름, 이메일, 제목 등)을 나타내고, text는 길고 가변적인 긴 문자열(본문, 설명 등)을 나타낸다.
    - uuid : ERD에서는 uuid를 그 자체로 하나의 타입명으로 기재한다. 표준으로 정해진 고정 포맷이 있기 때문에 전용 타입명을 쓰는게 훨씬 명확하다.
- **ERD 관계선은 데이터가 FK로 실제 연결되어 있는지를 나타냄**
    - 애플리케이션 로직상의 이벤트 흐름과는 다르다.
- **다형성 구조와 JPA**
    - 다형성 구조의 테이블은 다른 테이블과 FK로 직접 연결되지 않는다. 따라서 명시적으로 한 번 더 조회가 필요하다. (일반적인 FK 관계였다면 JOIN으로 한 번에 조회 가능)
    - FK 제약이 없어서 무결성은 DB 수준에서 검사 불가하다. (애플리케이션이 책임)
    - JPA는 FK 기반 연관관계(@OneToMany, @ManyToOne)를 중심으로 설계된 ORM이기 때문에 다형성 구조는 JPA의 정규 매핑 방식으로 표현되지 않는다.
    - Native Query / QueryDSL로 직접 조회 - 매번 수동으로 조건을 걸어야 하며, @Entity 간 자동 연관관계 매핑을 포기해야 한다.
- **다형성이 선호되는 상황**
    1. 대상 엔티티 종류가 많으며 계속 늘어날 가능성이 있는 경우
        - 횡단 기능(cross-cutting feature)으로 인한 코드 중복을 줄여준다.
    2. 조회보다 집계가 중심인 기능
    3. 로그성 테이블인 경우
        - 개별 조회 최적화보다 통합 기록이 목적인 경우
- **MySQL에서의 ENUM 사용**
    - ENUM 값을 추가하거나 변경할 경우 ALTER TABLE 명령을 사용해야 한다. 즉, 테이블의 스키마가 변경되는 것이다. (서비스 운영 중일 상태일 경우 특히 비용이 큼)
    - ENUM이 존재하지 않거나, ENUM의 문법과 제약이 다른 DB로 마이그레이션할때, ENUM 정의를 다시 작성해야 한다.
    - DB 컬럼은 VARCHAR로 두고, ENUM 구현과 값 검증은 애플리케이션 레벨에서 수행한다.
